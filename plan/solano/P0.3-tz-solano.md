```jsonc
// Ф3 (wallet-only):
{

  "dependencies": {
    "@me2em/crypto": "^1.1.0-rc.2 <2.0.0-0",                         // slip10 — Ф-crypto; workspace:^ при publish → ^1.1.0-rc.2 (Н-3)
    "@scure/base": "^2.4.0"                                          // base58 адресов/reference

  "devDependencies": { "@me2em/core": "workspace:^", "@me2em/crypto": "workspace:^" }
}
// Ф4 добавляет: "@noble/curves": "^1.8.1"   // on-curve для verifyWalletBinding; версия выровнена с deps @me2em/crypto
// Ф5 добавляет: "@solana/kit"               // единственный SDK, regular dep
```

- **`@me2em/core` — peer (как в редакции 1):** ровно один инстанс core в процессе. Три причины: (1) классовая идентичность — `instanceof AttestationError`/`DisposedError` и сопоставление по `code/level` обязаны работать через границу пакетов; (2) реестр адаптеров `globalThis[Symbol.for('me2em.paymentAdapters')]` переживает дубли, но `WeakMap`-привязки живут в модуле core — двойной core означает двойные хранилища привязок; (3) диапазон `<2.0.0-0` разрешает и rc-, и stable-ветку (`^1.0.0-rc.3` НЕ пропустил бы `1.1.0-rc.1` — пререлиз-компаратор совпадает только по [major.minor.patch]-кортежу).
- **`@me2em/crypto` — обычный dep (утверждено v1.2 §9 Ф3):** `crypto.slip10` — чистые stateless-функции; дубль инстанса безвреден, классовой идентичности не требуется.
- **Никаких прямых `@noble/*` в Ф3** (изменение против редакции 1: прямые `@noble/hashes`/`@noble/ed25519` удалены): HMAC-SHA512 и ed25519-публичники для SLIP-0010 живут в `@me2em/crypto` (Ф-crypto: `@noble/hashes` для HMAC, ed25519 — через уже присутствующий в deps crypto `@noble/curves`). Правило «не импортировать транзитивные зависимости напрямую»: **Ф3 не импортирует `@noble/curves`; Ф4 добавляет его как прямой dep (не через crypto)** — с версией, выровненной с crypto (один инстанс в графе pnpm). `@noble/curves` не требует init-модуля (в отличие от standalone `@noble/ed25519`) — `ed25519-init.ts` из редакции 1 удалён.
- **Почему нет `@scure/bip39`:** мнемоника→seed — зона core (`get64ByteSeedFromMnemonic`); solano принимает **готовый 64-байтовый seed**, не сырую мнемонику.
- **Почему нет `@solana/kit` в Ф3/Ф4:** единственный SDK — в **Ф5** (отдельный PR). Ф3 — адресная криптография поверх `crypto.slip10`, Ф4 — голый JSON-RPC `fetch`.

## 4. Сети и CAIP-2

| Сеть (SolanaNetwork) | Ключ реестра (CAIP-2) | Публичный RPC (default Ф4, переопределяется) |
|---|---|---|
| `mainnet-beta` | `solana:mainnet-beta` | `https://api.mainnet-beta.solana.com` |
| `devnet` | `solana:devnet` | `https://api.devnet.solana.com` |
| `testnet` | `solana:testnet` | `https://api.testnet.solana.com` |
| `localnet` | `solana:localnet` | конфигурируется приложением (только тесты) |

- **Грамматика vs значения (v1.2 §0.3):** CAIP-2-грамматика и helpers (`isValidChain`/`parseChain`) — в core; конкретные значения — эта таблица. `core` не знает `solana:*`, solano не парсит CAIP-2 сам.
- **Обоснование cluster-name reference:** де-факто стандарт экосистемы кошелков Solana (wallet-standard-цепи и Solana Pay tooling оперируют `solana:mainnet-beta`/`solana:devnet`); читаемость в подписанных аттестациях (аудитор видит chain глазами); иммунность к genesis-reset тестнета (genesis-hash-reference менялся при reset — кластерное имя стабильно).
- **Известные другие формы не поддерживаются и не алиасятся:** строгая форма CAIP-2-реестра (base58 genesis hash) и алиас `solana:mainnet` — другие ключи. Реестр требует точного совпадения; один chain — ровно одна строка таблицы. Иллюстративные `'solana:mainnet'` v1.2 §1.1 не нормативны — нормативна эта таблица (согласовано с P0.2).
- **`solana:localnet` — solano-специфичное значение (правка вердикта P0.3):** в CAIP-2-реестре отсутствует; только для тестов и локальной разработки — никогда в проде и в аттестациях реальных сущностей; RPC всегда конфигурируется приложением.

## 5. Ф3 — wallet-only (релиз rc.1)

### 5.1 Крипто-основа: `crypto.slip10` (Ф-crypto, `@me2em/crypto` 1.1.0-rc.1)

SLIP-0010 ed25519 реализуется **в `@me2em/crypto`** (v1.2 §9 Ф-crypto), solano определяет только контракт потребления:

- `slip10.masterKeyFromSeed(seed): { key: Uint8Array; chainCode: Uint8Array }` — `I = HMAC-SHA512(Key = "ed25519 seed", Data = seed)`; `IL` — master key, `IR` — chain code. Для ed25519 любая `IL` валидна — retry-цикл master-генерации не нужен.
- `slip10.deriveHardened(...)` / `slip10.derivePath(path)` — **только hardened** CKDpriv: `I = HMAC-SHA512(Key = cpar, Data = 0x00 ‖ ser256(kpar) ‖ ser32(i))`; `ki = IL`, `ci = IR`; `ser32(i)` — big-endian; `i ≥ 2³¹`. Нормальная деривация для ed25519 не определена — не-hardened компонент → failure (`TypeError`).
- **Seed-контракт (зазор р):** ровно **64 байта** — тот же, что у `Identity.fromSeed` (и верхняя граница SLIP-0010: 512 бит); иначе `TypeError`. Контракт реализуется и тестируется в Ф-crypto; JSDoc: «same seed contract as `Identity.fromSeed` (64 bytes)».
- ed25519-публичник из 32-байтового ключа — `@noble/curves` (уже в deps crypto); экспорт — namespace `slip10`.
- **Зависимости Ф-crypto (правка вердикта P0.3, следствие для solano):** slip10 runtime использует `@noble/curves` — в `@me2em/crypto` он **уже** regular dep (`^1.8.1` в `dependencies`, проверено по package.json; перевода из devDependencies не требуется); для HMAC-SHA512 Ф-crypto добавляет `@noble/hashes` **прямым** dep (сейчас приходит только транзитивно через `@noble/curves`). Следствие для P0.3: **Ф3 не импортирует `@noble/curves` и не полагается на его транзитивное присутствие; Ф4 добавляет его как прямой dep (не через crypto)** — версия выровнена с crypto (§2).
- **Тесты Ф-crypto:** TV1/TV2 ed25519 из slip-0010.md **дословно** (Приложение A) + негативы (не-hardened индекс; seed ≠ 64 байта). solano эти таблицы не дублирует.
- **Адрес (уровень solano):** `base58(publicKey)` от 32-байтового ed25519-публичного ключа, без чексуммы (стандарт Solana). `isValidAddress`: строгий base58-decode → ровно 32 байта; чистая функция, без сети, без on-curve (on-curve — только в `verifyWalletBinding`, Ф4 §6.3).
- **Схема путей solano (утверждена ранее, Документ 1):** `m/44'/501'/{index}'/0'`, `0 ≤ index ≤ 2³¹−1`.

### 5.2 `SolanaWalletTree` (`src/wallet-tree.ts`)

```ts
class SolanaWalletTree {
  static fromSeed(seed: Uint8Array): SolanaWalletTree;
  deriveWallet(index: number): Promise<{
    address: string;          // base58 publicKey
    privateKey: Uint8Array;   // 32B — см. wipe-требование ниже
    derivationPath: string;   // m/44'/501'/{index}'/0'
  }>;
  nextIndex(usedPaths: string[]): number;
  static deriveForVerification(seed: Uint8Array, path: string): Promise<string>;  // (Ф4) Mode 1
  dispose(): void;
}
```

- `fromSeed` — **consume seed (копию)** (v1.2 §4.1): валидация 64B → `crypto.slip10.masterKeyFromSeed` → `#masterKey`/`#masterChainCode` (приватные поля) → локальная копия seed **стирается**, seed не retain. **Caller'ский seed НЕ стирается** — caller owns it (формулировка v1.2 §4.1/§6.1; JSDoc: «copies internally, does not retain; does not wipe the caller's seed»).
- `#masterKey` приватно; `dispose()` — wipe обоих полей; после dispose любой метод → `DisposedError` из core (классовая идентичность через peer).
- **`deriveWallet` и зазор с:** JSDoc обязательное требование — «caller MUST wipe `privateKey` after use»; solano предоставляет собственный локальный helper `wipeBytes` (fill 0), не экспортируя его как часть API (в замороженной поверхности core `wipe` отсутствует).
- **`nextIndex(usedPaths)`** — реализация семантики v1.2 §2.2 (зеркало JSDoc Ф1, включая зазор н — «после фильтрации пусто → 0»):
  - парсер `parseSolanaPath`: путь начинается с `m/`, все компоненты hardened-числовые (`'`), `44'` на позиции 1, `501'` на позиции 2; индекс = первый числовой компонент после `501'` (4-й); 5-й компонент, если есть, должен быть числовым и игнорируется. Так распознаются и наши `m/44'/501'/5'/0'`, и «фантомские» `m/44'/501'/5'` (3-level, Phantom/SLIP-0010) — сторонние аккаунты не наступают на наши индексы. Padded renderings (`00`, `007`) игнорируются (canonical grammar `(0|[1-9][0-9]*)` — В-1).
  - неразборчивый путь — игнорируется, не бросается (толерантность к смешанному входу);
  - пусто после фильтрации → `0`; иначе `max(индексы) + 1` — дыры не переиспользуются;
  - фильтрация путей по `subjectWalletChain` — на вызывающем (chain-агностично по payload-полю), адаптер получает только свои пути (v1.2 §2.2).
- **`deriveForVerification` (Ф4, v1.2 §6.1)** — статический helper Mode 1, ~5 строк: `fromSeed(копия)` → `deriveWallet(parsePath(path)).address` → `finally dispose()`. JSDoc: «does not wipe `seed` — caller owns it». Только Mode 1; Mode 2 path не использует.
- Поток Ф3 (утверждённый): `tree.deriveWallet(i)` → `entity.bindWallet(descriptor)` → `Attestation.issue(..., opts.subjectWallet*)`.

### 5.3 `SolanaWalletAdapter` (`src/adapter.ts`)

```ts
// Ф3: implements WalletAdapter; с Ф4 удовлетворяет PaymentAdapter
class SolanaWalletAdapter {
  get chain(): string;                     // CAIP-2 из §4 (chain-bound view)
  isValidAddress(address: string): boolean;
  resolveWallet(entity: WalletEntityRef,
                opts?: { seed?: Uint8Array; index?: number }): Promise<WalletDescriptor>;
  nextIndex(usedPaths: string[]): number;  // обязательная реализация (не optional): solano всегда знает аллокацию
}
```

- **chain-bound views — механизм «один экземпляр — несколько ключей» (v1.2 §2.1) при сигнатуре `registerWalletAdapter(adapter)` (§8 v1.2).** Один state-объект (без сети, без ключей в Ф3) создаётся один раз; для каждой запрошенной сети создаётся лёгкое представление с собственным `chain` (прототипная делегация: `Object.create(state, { chain: { value: caip2 } })`), и каждое регистрируется через `registerWalletAdapter(view)`. Итог: один инстанс состояния, N записей реестра, `view.chain` всегда совпадает с ключом записи, disposer — по записи.
- `resolveWallet(entity, opts)`: без `opts.seed` → Promise reject `TypeError` (solano — детерминированный адаптер, без seed деривация невозможна); `index ?? 0`; внутри: `SolanaWalletTree.fromSeed(seed)` → `deriveWallet(index)` → сборка `WalletDescriptor { chain, address, derivationPath, label: entity.name }` → `tree.dispose()` в `finally`. Приватный ключ наружу не выходит — wipe внутри. `entity` — только метаданные (`id`/`kind`/`name` в `label`); в деривацию не входит (путь индекс-only — утверждено (е)).
- `isValidAddress` — §5.1.

### 5.4 `reference.ts`

- `generateReference(): Uint8Array` — 32 случайных байта `crypto.getRandomValues` (глобальный crypto, Node ≥22 и браузеры);
- `referenceToBase58(bytes)` / `referenceFromBase58(str): Uint8Array | null` — строгая проверка 32 байт.
- `reference` включается в транзакцию как **read-only non-signer key** (Solana Pay Specification v1) — добавление в транзакцию — Ф5; в URL — §5.5; в `getSignaturesForAddress(reference)` — Ф4. Дедупликация заказов приложением — по этому reference (app-level REPLAYED, v1.2 §5.3).

### 5.5 `url.ts` — `createPaymentRequestURL` (Solana Pay Specification v1)

Форма: `solana:<recipient>?amount=<..>&reference=<..>&spl-token=<..>&label=<..>&message=<..>&memo=<..>`

Состав `PaymentRequest` зафиксирован v1.2 §0.1: `{ chain, payTo, amount, asset, reference, expiresAt }` — маппинг:

- `payTo` → `recipient` (base58 адрес получателя);
- `amount` → `amount` — десятичная строка (SOL, не lamports; для SPL — единицы токена), без экспоненты; парсинг/округление — политика приложения;
- `reference` → `reference` — base58 32-байтного массива; Solana Pay допускает несколько `reference`-параметров, **solano выдаёт один** (модель дедупа протокола ключуется на один reference);
- `asset` → `spl-token` при SPL-запросе (mint, base58); поддержка в Ф3/Ф5 — открытый вопрос ТЗ-5;
- `chain` → в URL не попадает: URL строится view'ом своей сети (§5.3), несоответствие — ошибка вызова;
- `expiresAt` → в Solana Pay v1 URL не выражается; проверка expiry — `verifyPayment` по подписанному request (v1.2 §5.2/§5.4);
- `label`/`message`/`memo` — **опциональные параметры самой функции** (в `PaymentRequest` их нет по v1.2 §0.1), незакреплённые протоколом; `encodeURIComponent`; `memo` попадёт в on-chain memo — в него не должно попадать чувствительное; **open до анализа x402 (Б-3)** — scope-reduce: deliberately absent в rc.2, x402 memo goes through extra.me2em.memo; add later if needed for direct flow.
- чистая функция, сеть не трогает. Бывший открытый вопрос ТЗ-1 закрыт по существу v1.2 §0.1; остаток (SPL, label/memo) — при реализации Ф3.

### 5.6 `register.ts`

```ts
type SolanaNetwork = 'mainnet-beta' | 'devnet' | 'testnet' | 'localnet';
function registerSolanaAdapters(options: { networks: SolanaNetwork[] }): () => void;
```

- `networks` обязателен и непуст; неизвестное значение → `TypeError`;
- создаёт **один** state-объект, регистрирует chain-bound view на каждую сеть (§5.3), возвращает **составной disposer** (снимает все записи; идемпотентен);
- last-wins при перезаписи занятого ключа и security-note («регистрация — привилегия trusted-кода; недоверенная зависимость может подменить адаптер `solana:mainnet-beta`») — обеспечивает core; solano повторяет предупреждение в README/JSDoc.

### 5.7 Acceptance Ф3 (definition of done)

1. **Крипто-основа:** TV1/TV2 ed25519 дословно — тесты `@me2em/crypto` (Ф-crypto) зелёные; негативы §5.1 падают как ожидается (вне solano, но acceptance-факт фазы).
2. **Phantom cross-check (главный якорь solano):** фиксированная тестовая 12-словная мнемоника → `get64ByteSeedFromMnemonic` (core) → `tree.deriveWallet(0).address` == адрес первого аккаунта **Phantom** при импорте той же мнемоники (Phantom: `m/44'/501'/0'/0'`) == `solana-keygen recover` с явным `--derivation-path m/44'/501'/0'/0'`. Значение адреса записывается в fixture теста с пометкой origin (заполняется при выполнении acceptance, не выдумывается). **Phantom cross-check — отложенный acceptance-факт (требует браузер/`solana-cli`); не блокер rc.2; активируется отдельным коммитом.**
3. **Байт-идентичность core:** rc-векторы после Ф1 не изменились (золотой тест зелёный; вне solano, но acceptance-факт фазы).
4. **Типовая совместимость:** `tsc` сборка против workspace core; `WalletDescriptor`/`WalletAdapter` — те же типы (peer).
5. **Пакет:** `npm pack` → peer core + deps `@me2em/crypto`, `@scure/base`; чистый `pnpm install` в стороннем проекте резолвится без дублей @noble/@scure.
6. **Реестр:** `registerSolanaAdapters({ networks: ['mainnet-beta', 'devnet'] })` → `getWalletAdapter('solana:mainnet-beta')` и `getWalletAdapter('solana:devnet')` возвращают views одного состояния; disposer снимает обе записи; повторный `register` перезаписывает с предупреждением (last-wins).

## 6. Ф4 — `verifyPayment` (релиз rc.2)

### 6.1 Транспорт

- Голый `fetch` JSON-RPC к endpoint сети (§4; переопределяется опцией конструктора Ф4). Никаких SDK.
- Методы: `getTransaction(txRef, { encoding: 'json', maxSupportedTransactionVersion: <текущая> })`, `getSignaturesForAddress(referenceBase58)`, `getAccountInfo` (resolve LUT, кэшируется — §6.2).
- ⚠️ **Формат транзакций:** transaction v1 активен в mainnet/devnet/testnet с сентября 2026 (SIMD-0385) — раскладка message отличается от legacy/v0. Фикстуры Ф4 обязаны покрывать **оба** формата; парсинг — по RPC JSON-структуре (`message.accountKeys` + разобранные инструкции), не по сырым байтам; точные формы ответов RPC пинятся синтетическими фикстурами при реализации.

### 6.2 Оркестрация `verifyPayment(txRef, request)` — нормативный порядок (v1.2 §5.4)

Идемпотентный чистый read (v1.2 §5.3). Порядок и причины — **нормативны** (решения 17–18; Д-4 и Д-5 редакции 1 сняты):

| Шаг | Проверка | Причина при провале |
|---|---|---|
| 1 | транзакция существует и подтверждена (`getTransaction`) | `NOT_FOUND` (retry-able) |
| 2 | **reference containment (зазор у):** `request.reference` присутствует среди account keys транзакции — **static keys ИЛИ LUT** (LUT resolve через `getAccountInfo`, кэшируется) | **`REFERENCE_MISMATCH`** |
| 3 | время платежа: `blockTime` транзакции (fallback `observedAt`) после `request.expiresAt` | `EXPIRED` — политика v1.2 §5.2: block time предпочтительнее `observedAt`, защита от ложно-EXPIRED при опоздавшем наблюдении |
| 4 | chain-level REPLAYED: `getSignaturesForAddress(request.reference)` → более одного подтверждённого трансфера с данным reference | `REPLAYED` — детерминированно, без состояния (упрощение v1: считаем подтверждённые транзакции с reference, не классифицируя их как трансферы — консервативно, ложно-REPLAYED безопаснее пропуска). App-level дедуп по заказам — приложение (v1.2 §5.3) |
| 5 | получатель перевода == `request.payTo` | `WRONG_RECIPIENT` |
| 6 | сумма ≥ `request.amount` | `UNDERPAID` |
| 7 | успех | `PaymentResult` (состав — v1.0 §3.3, без изменений к v1.2 §12; сверить при реализации — ТЗ-2) |

- **Почему containment раньше time (v1.2 §5.4):** иначе чужой txRef с истёкшим временем ложно вернёт `EXPIRED` — а это **не наш** платёж. `REFERENCE_MISMATCH` — точная семантика «эта транзакция не исполнение **этого** request».
- **Breaking-природа (v1.2 §5.4, §0.2):** `REFERENCE_MISMATCH` — additive в enum, но breaking для exhaustive-switch потребителей (TS compile error); CHANGELOG с `**Breaking:**`. **Fail-safe для consumers:** unknown `PaymentFailureReason` MUST трактоваться как `REJECTED` (не «success»).
- `observedAt` = момент наблюдения адаптера (unix seconds), informational, в валидации не участвует; проставляется на всех исходах (v1.2 §5.2).

### 6.3 `verifyWalletBinding` — override адаптера

- Core default (v1.2 §6): `Attestation.verifySignature(token, issuerPublicKey)` + `subjectWallet === wallet.address`.
- Solano переопределяет, добавляя **on-curve**: base58-decode `subjectWallet` → 32 байта → валидация точки ed25519 через `@noble/curves` (`Point.fromHex` бросает на off-curve/невалидной кодировке → `false`); отсекает валидно-закодированные off-curve адреса.
- Mode 1 helper: статический `SolanaWalletTree.deriveForVerification(seed, path)` → address (§5.2; пере-деривация верификатором, владеющим seed); Mode 2 — без изменений (сознательное ограничение v1).

### 6.4 Тесты и acceptance Ф4

- Синтетические fixtures JSON-RPC (структуры реальных форматов v0 и v1, помечены синтетическими; никаких выдуманных «реальных» транзакций):
  - каждый шаг таблицы §6.2 в отдельности;
  - идемпотентность (двойной вызов — тот же результат);
  - fallback `blockTime: null → observedAt`;
  - REPLAYED (2 подписи с reference);
  - containment-негативы: транзакция без reference → `REFERENCE_MISMATCH` (не `NOT_FOUND`); **containment до time** — чужой txRef с истёкшим `blockTime` → `REFERENCE_MISMATCH`, не `EXPIRED`;
  - containment через **LUT** (fixture с `addressTableLookups`, reference не в static keys).
- Интеграционный (non-CI): devnet — реальный перевод с reference через URL-флоу → `verifyPayment` = успех; повторная оплата того же reference → `REPLAYED`.
