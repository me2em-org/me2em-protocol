## 0. Принципы

### 0.1. x402 — транспорт, не политика

x402 V2 — **транспорт платежа**. Он **не решает**:
- Кто платит (идентичность) — это attestation / Pact.
- Сколько платить (цена) — это `PaymentRequest` (продавец назначает).
- Как исполнять (сеть, актив) — это `PaymentAdapter` (`@me2em/solana` / будущий `@me2em/monero`).
- Кто подтверждает платёж — это **фасилитатор** (внешний сервис за интерфейсом `FacilitatorClient`).

x402 **делает**:
- Формирует 402-ответ (`PAYMENT-REQUIRED`).
- Принимает `PAYMENT-SIGNATURE`.
- Вызывает `FacilitatorClient.verify` / `.settle` (через приложение).
- Возвращает `PAYMENT-RESPONSE`.

### 0.2. Все параметры — из подписанных артефактов

Verifier получает все параметры из:
- `PaymentRequired` (подписан продавцом — `extra.me2em.sellerId`).
- `PaymentPayload` (подписан покупателем — `payload.signature`).
- Me2eM-расширения в `extra` (подписаны через `PaymentRequired` / Pact).

**Не требует** out-of-band параметров.

### 0.3. Слои и граф зависимостей

| Слой | Роль | Содержит |
|---|---|---|
| `@me2em/core` | Протокол: сущность и её свойства | `WalletAdapter`, `PaymentAdapter`, `PaymentRequest`, `PaymentResult`, `subjectWallet`, реестр адаптеров |
| `@me2em/x402` | **Транспорт платежа** | Кодек заголовков, `paymentFetch`, серверные помощники, `FacilitatorClient`, `extra.me2em` |
| `@me2em/solana` | Валютный пакет: Solana | `SolanaWalletAdapter`, `SolanaWalletTree`, **x402-сингнер Solana (M2)** |
| `@me2em/pact` | Сделка (отдельное ТЗ) | `PactJournal`, `verifyAct`; формат `agreementProof` |
| `@me2em/monero` | Гипотетический (не планируется) | — |

```
@me2em/core
   ▲        ▲        ▲        ▲
   │        │        │        │
 x402    solana    pact    (приложение)
```

**Правило:** `core` — единственный источник интерфейсов. Все остальные пакеты зависят **только** от `core` (peer). **Никаких перекрёстных runtime-зависимостей** между `x402`, `solana`, `pact`. Единственное санкционированное исключение — **type-only peer-зависимость** реализаций `PaymentSigner` от `@me2em/x402` (импорт контракта, ноль runtime-кода): `@me2em/solana` → peer `@me2em/x402` (M2, §4.2).

### 0.4. x402 опционален

Приложение может **не использовать** x402:
- Мессенджер с приёмом донатов: `core` + `solana` (прямой платёж через Phantom URL).
- Watch-only аудит: `core` + `solana` (`getWallet` без платежей).
- Не-платёжные Pact-соглашения: `core` + `pact`.

**Сценарии сборки стека** (§9).

### 0.5. `agreementProof` — непрозрачный `Uint8Array`

`agreementProof` — **непрозрачный для x402** артефакт согласования. Приложение, использующее Pact, кладёт туда `evHash` + journal-суффикс (формат определяет `@me2em/pact`). Приложение без Pact оставляет пустым. **x402 не интерпретирует** `agreementProof` — только передаёт через `extra.me2em.agreementProof` (base64-сериализация `Uint8Array`).

### 0.6. Совместимость — по политике проекта

Замороженных пакетов нет; обратная совместимость не нужна (пользователей нет), миграции не пишем. Формулировки документации меняются свободно, если это улучшает дизайн. Единственное постоянное правило для потребителей: **unknown enum-значения обрабатываются fail-safe** (никогда не трактуются как успех) — см. §0.7.

### 0.7. Fail-closed

Неизвестная версия x402, схема, сеть, `errorReason`/`me2emError` от фасилитатора — всегда отказ, никогда «успех».

## 1. Границы пакета `@me2em/x402`

### 1.1. Входит

- Кодек заголовков `PAYMENT-REQUIRED` / `PAYMENT-SIGNATURE` / `PAYMENT-RESPONSE` (base64-JSON x402 v2).
- Клиентский транспорт: `createPaymentFetch`, `PaymentSigner` (контракт), `readSettlement`.
- Серверные помощники: `paymentRequiredResponse`, `readPaymentHeader`, `settlementHeader`.
- Серверный конфиг: `X402Config` + `assertValidX402Config` (§3.10), ошибка `X402ConfigError`.
- Me2eM-расширение: `extra.me2em` (`sellerId`, `memo`, `reference`, `agreementProof`, `buyerId`).
- `FacilitatorClient` — интерфейс.
- `B402Facilitator` — HTTP-клиент к внешнему B402 (subpath `./b402`, opt-in).
- Ошибки: `X402ErrorCode` (клиентские) + реэкспорт `Me2emErrorCode` (из core).

### 1.2. Не входит

- Реализация фасилитатора — **отдельное ТЗ** (`@me2em/facilitator`).
- Pact-переговоры — **отдельное ТЗ** (`@me2em/pact`); только формат `agreementProof` упоминается.
- `PaymentAdapter` реализации — `@me2em/solana` / будущий `@me2em/monero`.
- `@me2em/x402/dev` (binance-константы) — **отдельное ТЗ**.
- HTTP-middleware (Express/Fastify/Hono) — **вне v1**.
- x402 v1 — **не поддерживается**.
- Подписки/рекуррентные платежи, стриминг/SSE, Bazaar/discovery — **не в треке**.
- React-хуки — **не нужны** (отдельное ТЗ, если понадобится).

### 1.3. Зависимости

```jsonc
// @me2em/x402 package.json
{
  "peerDependencies": { "@me2em/core": ">=1.0.0-rc.5 <2.0.0-0" },
  "devDependencies": { "@me2em/core": "workspace:^" }
}
```

**Нет** прямых runtime-зависимостей (только глобальный `fetch`). `@noble/*`, `@scure/base`, `@solana/kit` — **не** импортируются.

## 2. Изменения в `@me2em/core` 1.0.0-rc.5 (M0) — реализовано (rc.5, merge `b1916db`)

### 2.1. Новый модуль `packages/core/src/payment-x402.ts`

Dependency-leaf (как `payment.ts` — не импортирует ничего из `src/`, кроме `parseChain` из `payment.js`). Только типы и чистые гарды, **ноль runtime-зависимостей**, ноль сетевого кода.

Типы — ровно по схеме x402 v2:

```ts
export const X402_VERSION = 2;

export interface X402ResourceInfo {
  readonly url: string;                       // absolute http(s)
  readonly description?: string;
  readonly mimeType?: string;
  readonly serviceName?: string;              // printable ASCII, ≤ 32
  readonly tags?: readonly string[];          // ≤ 5, каждый ≤ 32
  readonly iconUrl?: string;                  // absolute http(s), ≤ 2048
}

export interface X402PaymentRequirements {
  readonly scheme: string;                    // 'exact', 'eip3009', 'permit2-exact', …
  readonly network: string;                   // CAIP-2, валидируется parseChain
  readonly amount: string;                    // atomic units, /^[0-9]+$/
  readonly asset: string;                     // адрес контракта / ISO 4217
  readonly payTo: string;
  readonly maxTimeoutSeconds: number;         // integer ≥ 1
  readonly extra?: Readonly<Record<string, unknown>>;
}

export interface X402PaymentRequired {
  readonly x402Version: 2;
  readonly error?: string;
  readonly resource: X402ResourceInfo;
  readonly accepts: readonly X402PaymentRequirements[];
  readonly extensions?: Readonly<Record<string, { info: object; schema: object }>>;
}

export interface X402PaymentPayload {
  readonly x402Version: 2;
  readonly resource?: X402ResourceInfo;
  readonly accepted: X402PaymentRequirements; // эхо выбранной опции
  readonly payload: Readonly<Record<string, unknown>>;
  readonly extensions?: Readonly<Record<string, { info: object; schema: object }>>;
}

export interface X402SettleResponse {
  readonly success: boolean;
  readonly errorReason?: string;
  readonly errorMessage?: string;
  readonly payer?: string;
  readonly transaction: string;
  readonly network: string;
  readonly amount?: string;
  readonly extra?: Readonly<Record<string, unknown>>; // Me2eM-расширения
  readonly extensions?: Readonly<Record<string, unknown>>;
}

export interface X402VerifyResponse {
  readonly isValid: boolean;
  readonly invalidReason?: string;
  readonly invalidMessage?: string;
  readonly payer?: string;
  readonly extensions?: Readonly<Record<string, unknown>>;
  readonly extra?: Readonly<Record<string, unknown>>;
}

export interface X402Supported {
  readonly kinds: ReadonlyArray<{
    readonly x402Version: number;
    readonly scheme: string;
    readonly network: string;
  }>;
  readonly extensions?: readonly string[];
  readonly signers?: Readonly<Record<string, readonly string[]>>;
}
```

Гарды (структурные, без сети): `isX402PaymentRequired`, `isX402PaymentRequirements` (в т.ч. `isValidChain(network)`), `isX402PaymentPayload`, `isX402SettleResponse`, `isX402VerifyResponse`, `isX402Supported`. Любое структурное нарушение → `false`/отказ, никогда исключение из гарда.

### 2.2. `Me2emErrorCode` — расширение `PaymentFailureReason`

### 2.3. Константы политики

```ts
export const BUYER_ATTESTATION_POLICY = {
  NONE: 'none', OPTIONAL: 'optional', REQUIRED: 'required',
} as const;
export type BuyerAttestationPolicy =
  typeof BUYER_ATTESTATION_POLICY[keyof typeof BUYER_ATTESTATION_POLICY];

export const REGULATORY_PROFILES = {
  NONE: 'none', KYC: 'kyc', AML: 'aml', AGE_GATED: 'age-gated', SANCTIONS: 'sanctions',

  typeof REGULATORY_PROFILES[keyof typeof REGULATORY_PROFILES];
```

**Семантика:** `BuyerAttestationPolicy` — декларация приложения о том, проверяет ли оно attestation покупателя. `RegulatoryProfile` — декларация compliance-режима. **x402 не enforce'ит** — только декларирует и fail-fast при логическом противоречии конфигурации.

### 2.4. `PaymentRequest.extra?` — Me2eM-метаданные

```ts
export interface PaymentRequest {
  // прямой флоу (Solana Pay); артефакт валютного уровня, x402-транспортом не используется
  readonly chain: string;
  readonly payTo: string;
  readonly amount: string;         // whole token units (см. «Единицы суммы» ниже)
  readonly asset: string;
  readonly reference: string;      // корреляция прямого флоу (Solana)
  readonly expiresAt: number;

  /** Me2eM-метаданные прямого флоу. В x402 — вложенный extra.me2em (§3.6). */
  readonly extra?: Me2emExtra;
}

export interface Me2emExtra {
  readonly sellerId?: string;
  readonly buyerId?: string;
  readonly memo?: string;
  readonly reference?: string;
  readonly agreementProof?: Uint8Array; // в x402 wire — base64 (X402Me2emExtra, §3.6)
  readonly [key: string]: unknown;
}
```

**Единицы суммы (В1, по приоритетам проекта):** у двух уровней — два нормативных формата, каждый закреплён своей внешней спецификацией. `PaymentRequest.amount` — **целые токен-единицы** (десятичная строка; семантика Solana Pay URI, валидируется `createPaymentRequestURL`). `X402PaymentRequirements.amount` — **atomic units** (строка `/^[0-9]+$/`; норматив x402 v2). Конверсия выполняется **один раз** в коде приложения при назначении цены (продавец строит `accepts[]` из своей цены); конверсионных помощников в пакетах нет, рантайм-конверсий внутри пакетов нет (минимум кода). Оба docstring'а и GLOSSARY фиксируют форматы.

**Верхнеуровневые `sellerId`/`buyerId`/`agreementProof` не добавляются (В4):** в rc.4 таких полей нет — депрекировать нечего, а deprecated-с-рождения поля загрязняют API. Me2eM-метаданные живут в `extra`: `PaymentRequest.extra` — прямой флоу, `requirements.extra.me2em` — x402. Сигнатуры `PaymentAdapter` (`pay`, `verifyPayment`) не меняются.

**Важно:** `PaymentRequest.reference` **не используется** в x402-транспорте; `PaymentAdapter` — валютный флоу (Solana Pay), `extra.me2em.reference` — x402 reconciliation.

Оставить как в core rc.4:

### 3.2. Кодек (`codec.ts`)

```ts
export function encodePaymentRequired(pr: X402PaymentRequired): string;
export function decodePaymentRequired(header: string): X402PaymentRequired;
export function encodePaymentPayload(p: X402PaymentPayload): string;
export function decodePaymentPayload(header: string): X402PaymentPayload;
export function encodeSettleResponse(s: X402SettleResponse): string;
export function decodeSettleResponse(header: string): X402SettleResponse;
```

**Правила:**
- Base64-JSON в значении заголовка. Декодер принимает base64 с паддингом и без.
- Отказ при невалидном base64 / не-JSON / структурном несоответствии → `X402Error` с `code: 'PAYMENT_REQUIRED_MALFORMED'` (для `PAYMENT-REQUIRED`), `'PAYMENT_PAYLOAD_MALFORMED'` (для `PAYMENT-SIGNATURE`), `'PAYMENT_RESPONSE_MALFORMED'` (для `PAYMENT-RESPONSE`).
- Лимит размера значения заголовка по умолчанию **8192 байт** (типичный лимит прокси на один заголовок), конфигурируемый. При превышении:
  - На стороне сборки (encode) — `TypeError` (программная ошибка).
  - На стороне разбора (decode) — `X402Error` с кодом `..._MALFORMED`.

### 3.3. Клиент (`client.ts`)

```ts
export interface SignerCapability {
  readonly scheme: string;
  readonly network: string; // CAIP-2
}

export interface PaymentSigner {
  readonly capabilities: readonly SignerCapability[];
  signPayment(
    requirements: X402PaymentRequirements,
    resource: X402ResourceInfo
  ): Promise<Record<string, unknown>>;
}

export interface PaymentFetchOptions {
  signer: PaymentSigner;
  selectRequirements?(accepts: readonly X402PaymentRequirements[]): X402PaymentRequirements;
  maxAttempts?: number; // default 2: initial + 1 with PAYMENT-SIGNATURE
}

export type PaymentFetch = (input: RequestInfo | URL, init?: RequestInit) => Promise<Response>;

export function createPaymentFetch(opts: PaymentFetchOptions): PaymentFetch;

export function readSettlement(response: Response): X402SettleResponse | null;
```

**Поведение `createPaymentFetch`:**
1. `fetch(input, init)` — исходный запрос.
2. Если `status === 200` — вернуть `Response` как есть (без подписи).
3. Если `status !== 402` — вернуть `Response` как есть (не наше дело).
4. Если `402` без `PAYMENT-REQUIRED` / битый — `X402Error` `PAYMENT_REQUIRED_MALFORMED` (fail-closed: не платим «по-старому»).
5. Если `402` с `PAYMENT-REQUIRED`:
   - `selectRequirements` (если задан) или первая опция, покрытая `signer.capabilities` (по `{scheme, network}`).
   - Если не найдено — `NO_VIABLE_OPTION` (без вызова `signPayment`).
   - `signer.signPayment(requirements, resource)` → `payload`.
   - Построить `X402PaymentPayload` с `accepted: requirements`, `payload`, `resource`.
   - `fetch(input, { ...init, headers: { ...init.headers, 'PAYMENT-SIGNATURE': encodePaymentPayload(...) } })`.
   - Вернуть `Response`.
6. Если `signPayment` бросил — `SIGNER_REJECTED` (пробросить).
7. **Не ретраить** после `PAYMENT-SIGNATURE`: повторный 402 / 5xx / сеть — вернуть `Response` как есть (нельзя платить дважды за один ресурс).

**`readSettlement(response)`:**
- `null` — заголовка `PAYMENT-RESPONSE` нет.
- `X402SettleResponse` — заголовок есть и распарсился.
- **throws** `X402Error` `PAYMENT_RESPONSE_MALFORMED` — заголовок есть, но битый (fail-closed: не игнорировать битый settlement как «нет заголовка»).

**Сингнеры:** контракт здесь, реализации — у владельцев ключей (chain-специфичные параметры — через конструктор реализации, контракт не меняется; пример — `getRecentBlockhash` в §4.4):
- `@me2em/solana` x402-сингнер (M2, §5).
- EVM-кошельки — сторона приложения (браузерный кошелёк, Agentic Wallet).
- Bitcoin — будущее, не планируется.

### 3.4. Серверные помощники (`server.ts`)

```ts
export function paymentRequiredResponse(pr: X402PaymentRequired, init?: ResponseInit): Response;
export function readPaymentHeader(
  headers: Headers,
  expectedResourceUrl?: string
): X402PaymentPayload | null;
export function settlementHeader(settle: X402SettleResponse): Record<string, string>;
```

**Правила:**
- `paymentRequiredResponse`: собирает 402 + `PAYMENT-REQUIRED` (base64). Body — опционально (JSON `PaymentRequired`).
- `readPaymentHeader`: `null` — заголовка нет. Если `expectedResourceUrl` задан и `payload.resource?.url !== expectedResourceUrl` → `X402Error` `RESOURCE_MISMATCH`.
- `settlementHeader`: `{ 'PAYMENT-RESPONSE': encodeSettleResponse(settle) }`.

**Оркестрация verify→settle** — **приложение**. Помощники нейтральны, не навязывают порядок. Рекомендованный порядок для B402: `verify` до выдачи ресурса, `settle` после (газ-спонсорство).

**Таблица порядка проверок** (приложение, рекомендованный порядок):

| # | Проверка | Кто |
|---|---|---|
| 1 | Структура `PaymentPayload` | x402 (decode) |
| 2 | `accepted` ∈ `accepts[]` из `PaymentRequired` | x402 (приложение) |
| 3 | `resource.url` соответствует текущему запросу | x402 (`readPaymentHeader` с `expectedResourceUrl`) |
| 4 | `FacilitatorClient.verify` | x402 (фасилитатор) |
| 5 | `extra.me2em.reference` — replay (через `PaymentAdapter.verifyPayment`) | приложение (адаптер) |
| 6 | Attestation (если `buyerAttestationPolicy !== 'none'`) | приложение (до x402) |
| 7 | Pact (если `agreementProof` есть) | приложение (до x402) |
| 8 | `FacilitatorClient.settle` | x402 (фасилитатор) |
| 9 | `PAYMENT-RESPONSE` | x402 (settlementHeader) |

### 3.6. `extra.me2em` (`me2em-extra.ts`)

```ts
export interface X402Me2emExtra {
  readonly sellerId: string;          // non-empty
  readonly buyerId?: string;
  readonly memo?: string;
  readonly reference?: string;
  readonly agreementProof?: string;   // base64(Uint8Array)
  readonly me2emError?: Me2emErrorCode;
  readonly [key: string]: unknown;
}

export function withMe2emExtra(
  req: X402PaymentRequirements,
  extra: X402Me2emExtra
): X402PaymentRequirements;

export function readMe2emExtra(req: X402PaymentRequirements): X402Me2emExtra | null;

export const X402_RESERVED_EXTRA_KEYS = [
  'assetTransferMethod', 'paymentFlow', 'name', 'version',
] as const;
```

**Правила:**
- `sellerId` — непустая строка. Отсутствие/тип не string → `ME2EM_EXTRA_INVALID` при записи; при чтении — `null` (не падать на чужих extra).
- `extra.me2em` — **вложенный** ключ; зарезервированные ключи x402 (`X402_RESERVED_EXTRA_KEYS`) не затираются.
- `withMe2emExtra` — **merge** с существующим `extra.me2em` (не overwrite): новое значение выигрывает при конфликте. Если `extra.me2em` есть, но не объект — `ME2EM_EXTRA_INVALID`.
- `readMe2emExtra` — читает **только** `extra.me2em`; чужие `extra` (top-level `sellerId` и т.п.) игнорируются, не считаются ошибкой.
- Компактность: суммарное значение заголовка ≤ 8 KiB.

**Два типа extra (имена разные намеренно — форматы разные):** core экспортирует `Me2emExtra` (прикладной, все поля optional, `agreementProof?: Uint8Array` — §2.4); x402 экспортирует `X402Me2emExtra` (wire-формат: `sellerId` обязателен, `agreementProof?: string` — base64, `me2emError?`).

### 3.10. `X402Config` — серверный конфиг (политика продавца), без enforcement

```ts
export interface X402Config {
  facilitator: FacilitatorClient;
  mode: 'stateless' | 'pact-aware' | 'auto';
  buyerAttestationPolicy?: BuyerAttestationPolicy;
  regulatoryProfile?: RegulatoryProfile;
  defaultChain?: string;
  defaultAsset?: string;
}
```

**Финальная формулировка (В2):** `X402Config` — серверный конфиг (политика продавца). `createPaymentFetch` его **не принимает**. Приложение вызывает `assertValidX402Config(config)` один раз при старте сервера; функция бросает `X402ConfigError` (extends `TypeError`, `code: 'CONFIG_INVALID'`, §3.7) на логических противоречиях. Клиент (`createPaymentFetch`) fail-closed по своим правилам (`NO_VIABLE_OPTION`, `PAYMENT_REQUIRED_MALFORMED`, `VERSION_UNSUPPORTED`, `SIGNER_REJECTED`) — без `X402Config`.

**`assertValidX402Config` — правила fail-fast (реализация в `server.ts`):**
- `facilitator` — объект с callable `verify`/`settle`/`supported`; иначе throw.
- `mode` — одно из `'stateless' | 'pact-aware' | 'auto'`; `buyerAttestationPolicy` (если задан) — из `BUYER_ATTESTATION_POLICY`; `regulatoryProfile` (если задан) — из `REGULATORY_PROFILES`; иначе throw (unknown enum — fail-closed, §0.7).
- `mode === 'stateless'` + `regulatoryProfile` задан и ≠ `'none'` → throw (KYC/AML требует Pact/attestation).
- `mode === 'pact-aware'` + `regulatoryProfile === 'none'` → допустимо (приложение само решает).
- `buyerAttestationPolicy`/`regulatoryProfile` — декларации; x402 **не проверяет** attestation per-payment (это делает приложение).

**x402 не валидирует `agreementProof` per-payment.** Только декларация в конфиге + fail-fast при старте.

## 4. `@me2em/solana` 1.1.0-rc.1 — x402-сингнер Solana (M2)

### 4.1. Scope

Реализует `PaymentSigner` из `@me2em/x402`:
- `capabilities` — явные CAIP-2 пары (wildcard `solana:*` не допускается — `parseChain` его не пропускает): `solana:mainnet-beta`, `solana:devnet`, `solana:testnet`; финальный набор — по контракту фасилитатора (§8.7).
- `signPayment(requirements, resource)` — подпись ключом из `deriveWallet()` (уже есть в `@me2em/solana`).
- Построение сообщения — **офлайн** (без RPC; блокхэш — инъекция, §4.4).

### 4.2. Зависимости

`@me2em/solana` уже имеет `@me2em/core` (peer), `@me2em/crypto` (direct), `@scure/base` (direct). Добавляется:
- `@me2em/x402` — peer `>=1.0.0-rc.1 <2.0.0-0` (**type-only**: импорт `PaymentSigner`/`SignerCapability`, ноль runtime-кода — санкционированное исключение §0.3).

`@solana/kit` **не добавляется** (ни runtime, ни dev): сериализация legacy transfer — ручная (компактный формат сообщения, system-program transfer), детерминированная и тестируемая golden-векторами; меньше зависимостей = быстрее импорт (приоритет «производительность → минимум кода»).

### 4.3. Структура

```
packages/solana/
├── src/
│   ├── ... (существующее)
│   └── x402-signer.ts   # SolanaX402Signer implements PaymentSigner
├── test/
│   └── x402-signer.spec.ts
└── package.json
```

### 4.4. API

```ts
export class SolanaX402Signer implements PaymentSigner {
  readonly capabilities = [
    { scheme: 'exact', network: 'solana:mainnet-beta' },
    { scheme: 'exact', network: 'solana:devnet' },
    { scheme: 'exact', network: 'solana:testnet' },
  ];
  constructor(opts: {
    tree: SolanaWalletTree;
    index?: number;                            // default 0
    getRecentBlockhash: () => Promise<string>; // инъекция источника блока (RPC у приложения)
  });
  signPayment(
    requirements: X402PaymentRequirements,
    resource: X402ResourceInfo
  ): Promise<Record<string, unknown>>;
}
```

**Правила:**
- `signPayment` использует `tree.deriveWallet(index)` (уже есть), строит Solana-транзакцию (перевод `amount` в `asset` на `payTo`; `amount` — atomic units → минимальные единицы сети, §2.4), подписывает.
- **Не** отправляет транзакцию в сеть — это `settle` (фасилитатор).
- `capabilities` — явные CAIP-2 сети, без wildcard (§4.1).
- `index` — default `0`; index allocation — через `nextPaymentIndex(usedPaths)` (свободная функция `wallet-tree.ts` — реальный API rc.1; метода `tree.nextIndex` нет).
- **Блокхэш — только инъекция** `getRecentBlockhash` (та же философия, что auth-инъекция §3.5); отсутствие — `TypeError` на конструкторе (fail-fast). RPC внутри сингнера нет.
- **Формат payload — `@experimental` me2em-конвенция** (§8.7): сериализация legacy transfer без `@solana/kit`, подпись ed25519 проверяется `verifyRaw` из `@me2em/crypto`; финальная фиксация — при появлении контракта солана-фасилитатора.

### 4.5. Критерии приёмки M2

- `SolanaX402Signer` реализует `PaymentSigner` из `@me2em/x402` (type-only импорт).
- `signPayment` возвращает валидный Solana-payload (подпись проверяется `verifyRaw` в тестах).
- `capabilities` — явные CAIP-2 сети, без wildcard.
- `tree.deriveWallet` используется; приватный ключ wipe'ится после подписи.
- `getRecentBlockhash` — обязательная инъекция; без неё конструктор бросает `TypeError`.
- e2e-тест: `SolanaX402Signer` + `createPaymentFetch` + mock-сервер (402 → PAYMENT-SIGNATURE → 200); payload-конвенция проверяется на моке (`@experimental`).
- golden-векторы ручной сериализации legacy transfer (детерминированные, офлайн).

2. Схема auth (API key / JWT / подпись+таймстемп), правила ротации.
3. Карта `scheme` ↔ `asset` (BSC mainnet: `U`, `USD1`, `USDT`, `USDC`; Solana: `sol`, SPL mint).
4. Сети (CAIP-2), поддерживаемые B402; testnet-сеть.
5. Лимиты и SLA (rate limits, таймауты, settle-идемпотентность).
6. Юридические/региональные ограничения.
7. Контракт солана-фасилитатора (сторонний или последующий этап B402): формат payload exact/Solana и источник blockhash (если поставляет фасилитатор). До этого — payload-конвенция `@experimental` (§4.4).

До получения 1–2 `B402Facilitator` — `@experimental`; M0–M2 от него не зависят.

## 9. Вне скоупа

1. **`@me2em/facilitator`** — отдельное ТЗ (отдельный пакет/сервис; в `@me2em/server` или standalone).
2. **`@me2em/pact`** — отдельное ТЗ; формат `agreementProof` (`evHash` + journal-суффикс) определяется там; x402 только передаёт base64.
3. **`@me2em/x402/dev`** — отдельное ТЗ (binance-константы, dev-facilitator).
4. **`@me2em/monero`** — гипотетический, не планируется (упоминается только в сценариях как пример).
5. **HTTP-middleware** (Express/Fastify/Hono) — вне v1.
6. **x402 v1** — не поддерживается.
7. **Подписки/стриминг/SSE/Bazaar** — вне.
8. **React-хуки** — вне.
9. **EVM-сингнер** — сторона приложения (вне Me2eM).
10. **Self-facilitate** внутри `@me2em/x402` — нет (это `@me2em/facilitator` или приложение).

## 10. Последующие треки (вне скоупа)

1. **`@me2em/facilitator`** — отдельное ТЗ: HTTP-сервер (`/verify`, `/settle`, `/supported`), RPC-ноды, auth, идемпотентность, duplicate settlement protection. Хостинг — SaaS / self-hosted / встроенный в `@me2em/server`.
2. **`@me2em/pact`** — отдельное ТЗ: `PactJournal`, `verifyAct`, формат `agreementProof`.
3. **`@me2em/x402/dev`** — отдельное ТЗ: binance-константы, dev-facilitator.
4. **Сторонние фасилитаторы** (x402.org, Coinbase, Base) — приложение реализует `FacilitatorClient` само.
5. **`@me2em/monero`** — не планируется.
