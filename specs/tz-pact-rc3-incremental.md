# ТЗ-дополнение: инкрементальная верификация Journal — rc.3 (F-rc3-1 / Б2)

**Дата:** 2026-11-24 · **Статус:** утверждено (план `specs/plan-pact-rc3.md`, Фаза 0)
**База:** pact rc.2 (`develop` = `aa1933b`), `specs/tz-pact.md` §3.3/§3.4, PACTS §7.7
**Решения этого документа:** RC3-D1 … RC3-D8 (нумерация отдельная, чтобы
не пересекаться с D-решениями PACTS).

---

## 1. Проблема (аудит Б2)

`finalize` (B-7) ре-верифицирует расширенный журнал целиком на каждую
сборку: полный replay — `validateEvent` + skew + Ed25519 + state
machine — O(N) на вызов, **O(N²)** на полный жизненный цикл. Для
2-party v0.1 приемлемо, но We2eM/AS с журналами в тысячи событий
требует инкрементального replay с **хэш-коммитнутым промежуточным
состоянием** (формулировка карточки BACKLOG).

## 2. Решение — `JournalVerifier`

Один проход кода верификации: батчевый `replay` переезжает на фабрику
(RC3-D8) — второго, «быстрого» пути нет; быстрый путь — только пропуск
**повторной** проверки уже закоммиченного префикса.

### RC3-D1 — хэш-коммит префикса

```
C_0 = 0^32
C_i = SHA-256(C_{i-1} ‖ SHA-256(TBS_i))        — 64-байтная конкатенация, сырые байты
evHash_i = b64url(SHA-256(TBS_i))
```

Коммит — детерминированная функция содержимого префикса: любое
изменение байтов любого префикс-события (включая перезаклейку `ph`
перезаписью цепочки) меняет `C_height`.

### RC3-D2 — integrity pass

`applySuffix(events)` при `height > 0` сначала перечитывает
переданный массив `[0..height)` **из фактического содержимого**:
pid/sq/ph-цепочка + пересчёт `C_height`. Расхождение с закоммиченным
значением ⇒ `FORK_DETECTED`. Полная проверка (`validateEvent`, skew,
подписи, state machine) выполняется только на суффиксе
`[height..len)`. При `events.length < height` — `FORK_DETECTED`
(«журнал короче закоммиченного префикса»).

Целостность префикса, проверенного верификатором ранее, таким образом
не доверяется вызову: подмена массива между вызовами обнаруживается
дешёвым проходом (JCS + 2×SHA-256 на событие — без Ed25519 и без
state machine).

### RC3-D3 — fail-closed без fallback

Расхождение коммита ⇒ `FORK_DETECTED @ verify` («journal prefix
diverges from the committed verifier state»), тихий пересчёт
запрещён. Точную причину (какое именно событие сломано) даёт
from-scratch диагностика — `verifyJournal`; fast path сообщать её не
обязан и не пытается (fallback замаскировал бы причину и породил бы
второй путь верификации).

### RC3-D4 — API

```ts
export class JournalVerifier {
  constructor(clock?: Clock, opts?: VerifyOptions)
  apply(event: Event): void            // полная проверка + применение одного события
  applySuffix(events: Event[]): void   // RC3-D2: integrity pass + суффикс
  get height(): number                 // число применённых событий
  get head(): string                   // evHash последнего применённого; ZERO32 — пусто
  snapshot(): VerifyResult             // как успешный verifyJournal (roster/pactRoot/journalHead/seq)
}
export function createJournalVerifier(clock?: Clock, opts?: VerifyOptions): JournalVerifier;
```

- Методы **бросают** `PactError` (стриминговый контракт — остановка на
  первом нарушении); `verifyJournal` сохраняет `VerifyResult`-обёртку.
- Состояние не публикуется (opaque); внутренний доступ `replay` —
  через module-private WeakMap, публичная поверхность класса чистая.
- `snapshot()` валиден только после успешных `apply*` (ошибка бросается
  до изменения состояния — apply атомарен: все проверки до мутаций).

### RC3-D5 — skew в стриминге

`Clock.now()` читается на каждом `apply` (батчевый replay читает один
раз). Для эпох-консистентных replay вызов пинует `Clock` (фиксированный
или `skewCheck: 'none'`) — тогда семантика идентична батчу. При
`skewCheck: 'none'` clock не читается вовсе.

### RC3-D6 — чекпоинт не сериализуется

Состояние верификатора — in-memory артефакт сессии: не wire-формат,
не проходит через `Channel`/`JournalStore`, не попадает в экспорт
журнала. Суффикс-верификация по **чужому** head — это `verifyPrefix`
(свой контракт доверия, B-7/D27). Граница зафиксирована намеренно:
сериализуемые чекпоинты — новая поверхность атаки и новый формат,
вне rc.3.

### RC3-D7 — интеграция сборки (single-slot cache)

`finalize` держит module-level single-slot кэш
`{ tail: Event; height: number; verifier }`:

- **hit** (`tail === events[last] && height === events.length`):
  `verifier.applySuffix(events)` (integrity-only) + `apply(newEvent)`;
  кэш обновляется под новое событие.
- **miss**: новый верификатор (`skewCheck: 'none'`, Б1) + полный
  replay — ровно поведение rc.2, без регрессии.
- Интерливинг двух журналов ⇒ промах на каждый вызов ⇒ rc.2-семантика
  (корректность без выигрыша); sequential lifecycle — выигрыш.
- Память: один верификатор, O(N).
- Кэш не обходится: на hit integrity pass re-derives chain + коммит
  из переданного массива (RC3-D2), подмена обнаруживается.
- Clock кэш-верификатора не читается (`skewCheck: 'none'`), поэтому
  различие clock разных вызовов не материально (Б1).

### RC3-D8 — один код пути

`replay(events, clock, skewCheck)` = `new JournalVerifier(...)` +
`applySuffix(events)` + внутреннее состояние. `verifyJournal`,
`verifyPrefix`, `verifyAct` — без изменений сигнатур и семантики.

## 3. Вектор атаки (нормативный тест)

Массив, где среднее событие подменено, а все последующие `ph`
перезаклейлены (цепочка консистентна; подписи перезаписанных
суффикс-событий fast-путём не перепроверяются):

- батчевый `verifyJournal` ⇒ `SIGNATURE_INVALID` (точная причина);
- кэш-верификатор на том же массиве ⇒ `FORK_DETECTED` (RC3-D2/D3).

Тест обязан существовать в `test/verify.spec.ts`; собрать его можно
без ключей атакующего — перезаклейка `ph` не требует подписей, чтобы
дойти до проверки коммита.

## 4. Асимптотика (измерено, `bench/baseline.json`)

| Путь | Стоимость |
|---|---|
| `applySuffix` на кэше | O(height) дешёвый проход — **~9 µs/событие** (64-событийный префикс: 0.59 ms) + O(suffix) полная проверка |
| Полный replay (rc.2-путь) | **~2.9 ms/событие** — доминирует Ed25519 (64 события ≈ 186 ms, 128 ≈ 349 ms) |
| Тёплая сборка | integrity(64) + один полный чек ≈ 3.5 ms против 186 ms в rc.2 — **~50×**; @128 — ~90× |
| Lifecycle N=1000 | Σ тёплых сборок ≈ единицы секунд против ~десятков минут rc.2 |
| Строгая O(1) на вызов | требует commitments в wire-формате — ломает байт-заморозку v1, вне rc.3 |

Бенчмарк `bench/journal.bench.ts` + `bench/baseline.json` фиксируют
числа (vitest bench; `--outputJson`).

## 5. F-rc3-2 — решение по существу (отклонение литеральной формулировки)

ТЗ §3.5: контракт `JournalStore` — time-free (P2: `Clock` — инъекция
verify/assemble; C3: skew — зона verify). Литеральный «опциональный
Clock в `MemoryStore.append`» нормативной опоры не имеет: dead-параметр
против минимализма (семейство В3). Содержательная часть находки —
скрытый O(N) на append (`currentHead()` пересчитывает `evHash`
последнего события на каждый вызов) — устраняется инкрементальным
кэшем head в `MemoryStore` (O(1) на append; семантика CAS не меняется).
Отклонение литеральной формулировки фиксируется здесь и в BACKLOG.

## 6. Критерии приёмки

1. Эквивалентность: инкрементальный результат (ok/код ошибки, roster,
   pactRoot, journalHead, seq) == батчевому `verifyJournal` на полном
   lifecycle-журнале, включая тампированные варианты.
2. Attack-тест §3 присутствует и проходит.
3. Регресс 108 тестов rc.2 — без правок ассертов.
4. Бенчмарк + `bench/baseline.json` закоммичены; per-event cost сборки
   не растёт с N.
5. Coverage ≥ 90% (пороги vitest сохранены); tsc/eslint чисто.

## 7. Не входит в rc.3

N-party assembly (F1) — v0.2; `rosterDigest` (BL-12/F8) — P3; любые
wire-изменения — запрещены derivation/byte-freeze; сериализуемые
чекпоинты — отклонены (RC3-D6); пересмотр `JournalStore`-контракта —
нет нормативной необходимости.
