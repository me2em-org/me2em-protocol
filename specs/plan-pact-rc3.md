**Дата:** 2026-11-24 · **Статус:** утверждено и исполнено — rc.3
(Ф0–Ф2 закрыты 2026-11-24; решения открытых вопросов §9: ТЗ инкрементального

**База:** `develop` = `aa1933b` (pact rc.2: 108 тестов, coverage 97%)
**Триггер:** единственный P2-пункт пакта (F-rc3-1, аудит Б2) + анализ

## 1. Контекст

rc.2 закрыл audit-hardening (Б1/Б4/Б5/Б6/Б7/Б8, В2/В4/В12; отклонены
Б3/В1/В3) и докрытия пост-ревью З2/З3. Из follow-up-ов (`BACKLOG.md`,
раздел «Pact (BL-58)») в rc.3 попадает:

- **F-rc3-1** — инкрементальный `verifyPrefix`: сборка ре-верифицирует
  весь префикс на каждое событие — O(N) за раз, **O(N²)** на полный
  жизненный цикл (аудит Б2). Единственный P2-пункт пакта.
- **F-rc3-2** — опциональный `Clock` в `MemoryStore.append` (мелочь,
  решено в `specs/plan-pact-rc2.md` §3).
- **F-rc3-5** — golden-векторы `pact` в `specs/test-vectors.json`:
  секция существует (rc.1), но не покрывает поведение, добавленное
  rc.2 (pinned `ep`, chain-liveness). Проверить и дополнить.

## 2. Цель rc.3

1. Сборка и верификация журналов длины N за **O(N)** вместо O(N²)
   при неизменных гарантиях безопасности (fail-closed сохраняется).
2. Синхронизация golden-векторов с rc.2-семантикой.
3. Зафиксировать трассировку «We2eM v2.1 → pact» (§7) — без изменений
   протокольных форматов в этом релизе.

## 3. Не-цели rc.3 (фиксируются)

- **N-party assembly (F1)** — v0.2. Федерация We2eM (M5) стартует с
  двух нотариусов; 2-party pact rc.2 (INVITE/ENROLL/EVICT/AMEND/th/
  EXIT/ROTATE + Tier 3) её покрывает.
- **rosterDigest (BL-12/F8)** — P3, отдельное поле, `pactRoot` не
  переопределяется (вердикт по Б3).
- **Любые изменения деривации в core** — запрещены derivation-freeze
  rule (PLAN-LTS §4) до v1.0.0. Вывод `confirmKey` We2eM — зона ТЗ
  `@me2em/idp` со своим versioned info string, не core и не pact.
- **Движок нотариального Journal** (GENESIS/RENEW/EXIT/DISSOLVE/
  ROTATE_KEY, односторонняя подпись) — вне пакта. Пакт — модель
  симметричных пактов с paired binding (PACTS §7.8/D4); нотариальная
  модель концепция сама определяет как «не Pact в строгом смысле»
  (v2.1 §4.1). Прецедент выделения: A4 (solana → отдельное ТЗ/пакет).

## 4. Фаза 0 — Дизайн инкрементального replay (≈2–3 дня)

**Задача:** дополнение ТЗ (`specs/tz-pact.md` §3.4/§6 или отдельный
раздел) с фиксацией решений до кода.

**Решения, которые надо принять:**

1. **API-поверхность.** `verifyJournal(events, clock?, opts?)` остаётся
   stateless и референсной (from-scratch). Добавляется чекпоинтный путь
   — кандидат: фабрика `createJournalVerifier(clock?, opts?)` →
   `apply(event) | applySuffix(events)` с внутренним `ReplayState`
   (он уже существует как внутренняя структура `verify.ts` — «append-only
   views over the verified prefix», вынести наружу как opaque-значение,
   привязанное к evHash головы). Сборка (`finalize`) вместо полной
   ре-верификации префикса применяет суффикс к кэшированному состоянию.
2. **Инвариант целостности кэша.** `ReplayState` привязывается к
   evHash последнего применённого события; `applySuffix` проверяет
   `ph` первого нового события против головы состояния — расхождение
   ⇒ `PERHASH`-ошибка, а не тихий пересчёт. Тест-вектор атаки: подмена
   среднего события в загруженном журнале при повторном использовании
   состояния ⇒ отказ.
3. **Детерминизм.** Инкрементальный результат обязан быть побитово
   равен from-scratch (ok/error код/warnings) на случайных журналах —
   property-тест становится критерием приёмки.
4. **Граница применимости.** Суффикс-верификация по чужому чекпоинту
   (BL-10 pattern) — вне rc.3: чекпоинт не сериализуется и не передаётся
   по сети (in-memory only), иначе это новый wire-формат и новая
   поверхность атаки. Зафиксировать в ТЗ явно.
5. **(Опционально, решить в фазе)** — примечание в PACTS.md §5, что
   формула evHash (`SHA-256(JCS(event без sig))`) фиксируется как
   общий паттерн hash-chain журналов экосистемы (We2eM v2.1 §5.1
   строит Journal «по образцу PACTS §5»). Минимализм: не создавать
   общего модуля, idp повторяет ~30 строк по формуле из ТЗ.

**Критерий приёмки фазы:** решения 1–4 согласованы и внесены в ТЗ;
вектор атаки описан до реализации.

## 5. Фаза 1 — Реализация F-rc3-1 (≈3–5 дней)

1. Вынести `ReplayState` из `verify.ts` в публичный opaque-тип;
   `createJournalVerifier` + `apply/applySuffix`; `verifyJournal`
   переезжает на фабрику внутри (один проход кода верификации —
   никакого второго, «быстрого» пути).
2. `assemble/*`: `finalize` держит верификатор на префиксе и применяет
   суффикс (путь B-7 сохраняется: невалидный журнал не собирается).
3. Perf-бенчмарк `bench/`: сборка+верификация журнала N=1000 — время
   растёт линейно (фиксируется baseline-файл по конвенции PR-4).
4. Тесты:
   - property: инкрементальный == from-scratch (vitest-checkpoints
     или ручной прогон N случайных журналов из существующих фабрик);
   - атака из Фазы 0 (п. 2): подмена среднего события ⇒ отказ;
   - регресс существующих 108 тестов без правок ассертов.

## 6. Фаза 2 — Мелочи, векторы, документация (≈1–2 дня)

1. **F-rc3-2:** опциональный `Clock` в `MemoryStore.append`

## 8. Трассировка: We2eM v2.1 → pact/core (результат анализа, не код rc.3)

| Потребность We2eM v2.1 | Реализация сегодня | Статус |
|---|---|---|
| evHash = SHA-256(JCS(event без sig)) | `evHash` (pact codec) + `jcs.canonicalize` (core rc.9) | ✅ паттерн; idp повторяет по формуле ТЗ |
| Hash-chain (ph, sq, ZERO32) | pact codec/Journal | ✅ паттерн |
| Attestation, подписанная confirmKey | `Attestation.issue(signer, …)`; `Signer` = 1 метод → адаптер над derived-ключом в idp (~15 строк) | ✅ |
| scopes `idp:issuer=…@fp`, `idp:claim:domain=…` | `grant.scopes: string[]`, wildcard-запрет (в `scopes` нет wildcard — только `subNamePatterns`) | ✅ совместимо |
| `normalizeName` | core `canonical-name.ts` | ✅ |
| root(offline) → signing(online, 90д), compromisedAt | core Identity → `attestHandle` (TTL) + `RevocationChecker.isRevokedAt` (rc.9, dated) | ✅ прямое соответствие |
| Membership «paired binding» (домен+участник) | pact ACT (co-sign двух сторон); цепочка root→домен→участник = модель core Handle/SubHandle, MAX_DEPTH=2 = v2.1 §8.3 | ✅ (семантика) |
| Федерация M5, 2 нотариуса | pact rc.2 (2-party + AMEND(th) + Tier 3) | ✅ сегодня; ≥3 нотариусов → F1 (v0.2) |
| Journal: 5 типов, односторонняя подпись, пользователь-бенефициар | — | ✗ не pact (v2.1 §4.1 сама: «не Pact в строгом смысле») → ТЗ @me2em/idp |
| PoP challenge/nonce, Resolver, well-known, репликация | — | ✗ M1/M3 @me2em/idp, тривиальные примитивы |
| Suffix-верификация pact-журналов | verifyPrefix; инкрементально — **rc.3 (этот план)** | ⚠️ → rc.3 |
| O(N²) Б2 для AS/длинных pact-журналов | — | ⚠️ → rc.3 |

**Вердикт по достаточности:** для v0.1 We2eM (M1) pact как runtime не
нужен — нотариальный Journal строится на примитивах core (JCS, evHash-
паттерн, Attestation, dated revocation). Для M5 (федерация, 2 нотариуса)
pact rc.2 достаточен уже сегодня; rc.3 закрывает масштабирование (Б2) и
векторы. Изменений форматов под We2eM в pact не требуется.

**Критическая находка концепции (вне rc.3, до утверждения v2.1):**
§3.2/§4.3 утверждают, что verifier выводит `confirmPub` сам из
`we2em_pubkey` — в предложенной формуле `HKDF(IKM = we2em_signing_key)`
это невозможно: HKDF от публичного ключа сделать confirmKey публично
выводимым (подделка подписей домена), от приватного — верификатору
нечего подавать на вход. Корректные варианты: **(A)** HKDF от
приватного signing key; верификатор берёт `confirmPub` из Journal,
а смена поколений подтверждается цепочкой подписей (событие g несёт/
подтверждает confirmPub g+1) — это паттерн core root→handle;
**(B)** BIP32-style tweak (confirmPriv = signing_priv + t;
confirmPub = we2em_pub + t·B; t = HKDF(we2em_pub, info)) — вывод
офлайн из публичных данных, но нужен новый групповой примитив Ed25519
(только в idp, не core — freeze rule). Оба сохраняют «ключ не хранится»;
выбор — предмет ТЗ @me2em/idp.

   журналов экосистемы (rc.3)») — выполнено в rc.3.
